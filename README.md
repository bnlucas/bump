# Bump

A mobile-first dating + community app built on Next.js 16, with the
backend split across three domain-specific platforms:

| Concern | Backed by |
|---|---|
| End-user identity & sessions | **ShrouDB sigil** — schema-driven envelopes with Argon2 credentials and JWT sessions. |
| Social graph, matching, content | **Simbee** — users, affinities, signals, consent layers, vocab, content registry, scoring. |
| Realtime messaging | **Herald** — WebSocket streams with members, presence, typing, optional E2EE. |
| Encrypted blobs & KV | **ShrouDB** — `stash` for photos, `shroudb` for post/comment bodies, `courier` for notifications. |

The split is deliberate: Simbee keeps the relational matching graph
honest, ShrouDB keeps user-generated bytes encrypted at rest with
revocation, Herald handles only the realtime plane. Sigil owns auth
end-to-end so we never store password hashes in app code.

## What's in the app

- **`/auth`** — sign up / sign in via sigil envelopes
- **`/onboarding`** — first-run gate; needs display name + ≥1 consent
- **`/discover`** — context-aware swipe deck with photos, slide-out
  animation, consent-gated Herald stream creation on right-swipe
- **`/chat`** — match list with avatars
- **`/chat/[streamId]`** — Herald-backed realtime room with typing,
  pending/failed message states, and an offline-recipient push hook
- **`/communities`** — tagged feed (consent layer + topic), threaded
  comments, hydrated likes, filter pills sharing the active context
  cookie with Discover
- **`/profile`** — photos, name, bio, consent toggles, match
  preferences, interest chips, topic composer (preference + role +
  flags — the giver/receiver pairing Simbee scores on)

## Storage map

```
Profile name + bio          → sigil envelope + Simbee user.traits
Match preferences           → Simbee match_preferences
Photos                      → ShrouDB stash (revocable), ids in Simbee user.traits
Affinity tags + topics      → Simbee /users/{ext}/affinity/* (per consent layer)
Posts (title + body)        → ShrouDB shroudb namespace `posts`
Posts (existence + author)  → Simbee /content (for feed scoring)
Comments                    → ShrouDB shroudb namespace `comments`, prefix-keyed by parent
Likes                       → Simbee engagements
Conversations               → Herald streams `match-{a}-{b}`, derived from /matches
Active context              → bump.context cookie (shared across Discover + Communities)
Push notifications          → ShrouDB courier (default channel from env)
```

## Getting started

```bash
# 1. Install. The private SDKs live on GitHub Packages — set GITHUB_TOKEN
#    with read:packages before running install.
npm install

# 2. Configure. Copy .env.example to .env.local and fill in. None of the
#    env vars are read at module load — they're resolved lazily, so a
#    half-configured environment still boots the dev server (calls into
#    unconfigured engines fail at the network edge).
cp .env.example .env.local

# 3. Run.
npm run dev
```

## Scripts

- `npm run dev` — Next dev server.
- `npm run build` — typecheck + production build. Build runs against the
  unified Simbee spec; no env required.
- `npm run lint` — ESLint.
- `npm test` — Vitest. Unit tests cover the pure helpers (`cn`,
  `streamIdForPair`, `decodeJwtClaims`, `mintHeraldToken`, `isExpired`).
- `npm run generate-schema` — regenerates `src/lib/simbee-schema.ts`
  from `Simbee API.json` via openapi-typescript.

## Architecture notes

- **Typed Simbee client.** `src/lib/simbee.ts` constructs an
  openapi-fetch client over `src/lib/simbee-schema.ts` with Bearer-apiKey
  middleware. Every Simbee call lives behind `simbee().fetch.GET(...)`
  with full path/query/body checking. The one exception is
  `src/lib/simbee-raw.ts`, which exists solely for
  `/internal/v1/clients/{cid}/users/{ext}/affinity_tags` — the only
  endpoint we hit that isn't in the public spec.

- **Consent is the gate.** Discover swipes, conversation lookups, and
  the `/api/notify/dm` push all flow through `messagingAllowed`, which
  calls `/users/{me}/messages/check/{them}`. The pill row on
  `/discover` and `/communities` writes a shared `bump.context`
  cookie; granting a consent layer in `/profile` auto-creates the
  matching affinity via `ensureAffinity`.

- **Conversations are derived, not stored.** `/users/{me}/matches`
  filtered by `messagingAllowed` IS the conversation list. Stream ids
  are deterministic from the sorted user pair (`match-{a}-{b}`), so
  Herald streams are created lazily on first chat-open.

- **Notifications are best-effort.** Both new-connection and per-DM
  flows fire courier deliveries through `notifyUser`; failures are
  swallowed so they never block the action that triggered them. The
  per-DM route does its own server-side gating: stream membership
  both ways, recipient presence (skip if connected), permission
  re-check.

- **Photos go through an auth-proxy.** `/api/photos/[id]` retrieves the
  blob from ShrouDB stash, decodes the base64 plaintext, and returns
  it with the original content-type. Cache-Control `private,
  max-age=31536000, immutable` since stash ids are never reused.

## Things deliberately left for later

- **Hydrating attached affinity-tag chip state** on profile reload —
  blocked on the public spec exposing both `tag_id` and `affinity_tag_id`
  in a single response. Internal summary today gives only one of the two.

- **`/users/{me}/feed` for personalized Communities ordering** — needs
  a batch `/content/{id}` lookup to map FeedItemDto's `content_item_id`
  back to the `external_id` we use as a ShrouDB key.

- **Per-message DM push without a client ping** — Herald-admin in our
  SDK version doesn't expose webhooks, so the `/api/notify/dm` route is
  driven by the chat composer after `send()` resolves.
